# RDS Master Password Rotation Runbook

**Last updated:** 2026-05-18
**Audience:** Operator with AWS CLI access and Terraform state access
**Estimated time:** 5 min apply + ~2 min RDS modification + ~2 min ECS rollover

The RDS master password for `church-course-tracker-db` is generated by
Terraform (`resource "random_password" "db"` in
`infrastructure/secrets.tf`). It is **NOT** rotated automatically — rotation
is a deliberate manual operation.

---

## When to rotate

- **Required:** if the password has been exposed (committed to a repo, posted
  in a Slack channel, logged in cleartext, etc.).
- **Suggested:** quarterly hygiene.
- **NOT required:** every deploy (the password persists across deploys).

---

## Procedure

The rotation has four steps. The order matters: the application reads
DATABASE_URL from `app_secrets` Secrets Manager at container start, so we
must update that secret **before** ECS rolls, or new tasks come up with a
stale DATABASE_URL.

### 1. Generate a new password (in Terraform state)

```bash
cd infrastructure
terraform apply -replace=random_password.db -auto-approve
```

This regenerates `random_password.db.result` and propagates the new value
through:
- `aws_db_instance.main.password` → triggers an RDS `modify-db-instance`
- `aws_secretsmanager_secret_version.db_password.secret_string` → writes
  the new password to the standalone Secrets Manager entry `church-course-tracker-db-password`

The RDS resource has `apply_immediately = true`, so the password rotation
takes effect within ~30 seconds. During those 30 seconds the OLD password
still works for existing connections (Postgres keeps authenticated sessions
alive even after the master password changes).

### 2. Read the new password value out of Terraform state

```bash
NEW_PASSWORD=$(echo 'nonsensitive(random_password.db.result)' | terraform console | tr -d '"')
echo "Password is $(echo -n "$NEW_PASSWORD" | wc -c) characters"
# Do NOT echo $NEW_PASSWORD directly to the terminal.
```

### 3. Update the `app_secrets` DATABASE_URL with the new password

The app reads `DATABASE_URL` from `app_secrets`, not from the standalone
`db_password` secret. We need to URL-encode the new password and write the
full connection string:

```bash
python3 <<PYEOF > /tmp/new_app_secrets.json
import json, os, subprocess
from urllib.parse import quote

# Pull the current secret
r = subprocess.run(
    ["aws", "secretsmanager", "get-secret-value",
     "--secret-id", "church-course-tracker-secrets",
     "--region", "us-east-1",
     "--query", "SecretString", "--output", "text"],
    capture_output=True, text=True, check=True
)
current = json.loads(r.stdout)

# Substitute the new password
pw = os.environ["NEW_PASSWORD"]   # set this from step 2
encoded = quote(pw, safe="")
host = "church-course-tracker-db.cmn082g02d5u.us-east-1.rds.amazonaws.com"
current["DATABASE_URL"] = (
    f"postgresql://postgres:{encoded}@{host}:5432/church_course_tracker"
)

json.dump(current, open("/tmp/new_app_secrets.json", "w"))
PYEOF

NEW_PASSWORD="$NEW_PASSWORD" \
  aws secretsmanager put-secret-value \
    --secret-id church-course-tracker-secrets \
    --region us-east-1 \
    --secret-string file:///tmp/new_app_secrets.json
```

### 4. Force ECS to roll so new tasks pick up the new DATABASE_URL

```bash
aws ecs update-service \
  --cluster church-course-tracker-cluster \
  --service church-course-tracker-service \
  --force-new-deployment \
  --region us-east-1

# Wait for the rollover
until aws ecs describe-services \
        --cluster church-course-tracker-cluster \
        --services church-course-tracker-service \
        --region us-east-1 \
        --query 'services[0].deployments[0].rolloutState' \
        --output text 2>/dev/null | grep -q COMPLETED; do
  sleep 15
done
```

### 5. Verify

```bash
curl -s https://api.quentinspencer.com/health | python3 -m json.tool
# Expect: {"status": "healthy", ..., "checks": {"database": "healthy", ...}}
```

### 6. Securely delete the temp file

```bash
shred -u /tmp/new_app_secrets.json
```

---

## Expected impact

- **API availability:** the rotation typically causes a 1–2 minute window
  where new connections fail. Existing connections survive because Postgres
  keeps authenticated sessions alive after the master password changes.
  Once the ECS rollover completes (~2 min) the new task is healthy.
- **Other consumers:** none. The DATABASE_URL is only used by ECS.

---

## Rollback

If the rotation goes wrong (e.g., the new password contains characters that
don't URL-encode correctly):

1. Revert Terraform: `terraform apply -replace=random_password.db` again
   generates yet another password (this won't revert to the OLD password — it
   generates a NEW one). The OLD password is unrecoverable after step 1.
2. The application can survive a botched rotation only as long as existing
   tasks are alive (Postgres connection pool persists). If you have NOT yet
   forced the ECS rollover (step 4), you can recover by:
   - Reverting `app_secrets` DATABASE_URL to its previous version:
     ```bash
     aws secretsmanager list-secret-version-ids \
       --secret-id church-course-tracker-secrets --region us-east-1
     # Get the prior VersionId, then:
     aws secretsmanager update-secret-version-stage \
       --secret-id church-course-tracker-secrets \
       --version-stage AWSCURRENT \
       --remove-from-version-id <CURRENT_VID> \
       --move-to-version-id <PRIOR_VID> \
       --region us-east-1
     ```

If you DID roll ECS and the new password is broken, the only option is to
rotate again to a third password and re-do the procedure.
