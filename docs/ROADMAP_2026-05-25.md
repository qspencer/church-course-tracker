## TL;DR

Three Tier-1 items represent the only remaining *active* risk: an Angular
18→21 migration to close 9 high-severity XSS CVEs, moving the JWT out of
`localStorage`, and refactoring the inline-DDL in `backend/start.sh` to proper
Alembic migrations. Tier 2 is meaningful quality work. Tiers 3 and 4 are
hygiene and long-term investment. **Don't start Tier 2 work until Tier 1 is
done** — testing is valuable but doesn't reduce active risk.

| Tier 1 — Active risk | 3 items | ~7–11 days |
| Tier 2 — Meaningful improvement | 4 items | ~7–10 days |

## Tier 1 — Active risk (do these first)

### 1. Angular 18 → 21 migration (~3–5 days)

**Why first:** closes 9 high-severity XSS CVEs in `@angular/core` and transitive deps
(GHSA-jrmj-c5cx-3cw6, GHSA-prjf-86w9-mfqv, GHSA-g93w-mfhg-p222, plus animations
and common-package CVEs). These are real, patched in 19+, and currently shipping
to every user. `npm audit fix` already closed the lodash-es CVEs; Angular
requires `--force` (breaking).

**Why v21 instead of v19:** doing one combined jump now is less total work
than three separate windows later. v21 closes the same CVEs as v19 (the
affected range is bounded by `<= 18.2.14`), brings the project current with
the supported release line, and avoids the deprecation-cycle churn that hits
every Angular project that lags behind by 2+ majors.

**Scope:** multi-major-version bump. Angular's `ng update` is designed for
this but should be run **one major at a time**, not as a single
`@angular/core@21` jump (the migration schematics are applied per-version
and skipping versions can leave codemods unrun):

```bash
# From frontend/church-course-tracker/
ng update @angular/core@19 @angular/cli@19   # commit
ng update @angular/core@20 @angular/cli@20   # commit
ng update @angular/core@21 @angular/cli@21   # commit
```

Each step's commit isolates the codemod output for review, and a failure on
v20 doesn't force you to redo v19's migrations. After each step run
`ng build --configuration=production`, `ng test --watch=false --browsers=ChromeHeadless`,
and the backend suite via the e2e harness as a smoke test.

**Breaking changes to watch for** (read the per-version migration guides,
this is not exhaustive):

- **v19:** Standalone components become the default. The previous module-based
  bootstrap (`AppModule`) still works but `ng update` will offer to migrate
  to a standalone bootstrap. Recommend taking the migration since the
  module path will be removed in future majors.
- **v20:** Expanded signals + new control-flow syntax (`@if` / `@for`).
  Existing `*ngIf` / `*ngFor` continue to work; conversion is optional and
  the codemod is non-destructive.
- **v21:** Latest as of writing; check the CHANGELOG for current breaking
  changes (e.g., `HttpClient` defaults, removed deprecated APIs).

**Peer-library risk:** check that every direct dependency in `package.json`
supports v21 before starting. Likely points of friction:

- `@angular/material` and `@angular/cdk` (if used) — must move in lockstep
  with `@angular/core`
- `chart.js` + `ng2-charts` — `ng2-charts` has had Angular-version peer
  constraints in past releases
- `@sentry/angular` — Sentry's Angular SDK gets updated for each Angular
  major; check that a version supporting v21 exists
- Any third-party `@ngx-*` libraries — these are the most common stragglers
  on major-version bumps

For each, run `npm view <pkg> peerDependencies` to see the Angular range it
declares before starting.

**Done when:** `npm audit --production --omit=dev` reports 0 high-severity
vulnerabilities, `ng build --configuration=production` succeeds, the
frontend Karma suite passes, and the e2e suite passes against the upgraded
build.

**Rollback:** keep each per-major migration on its own commit; if v21
introduces a regression that's hard to chase, roll back to the v20 commit
and ship that. v20 also closes the CVEs (anything ≥ 19).

### 2. JWT → HttpOnly cookie (~2 days)

**Why second:** token currently lives in `localStorage` (`auth.service.ts:14`)
and CSP allows `'unsafe-inline' 'unsafe-eval'` (`main.py:118-129`). One
successful XSS today = full account takeover via token exfiltration. Moving to
an HttpOnly cookie set by the backend at login removes the XSS exfil path
entirely, *independent* of whether item #1 closes every CVE.

**Scope:**
- Backend: change `/auth/login` to set a `Set-Cookie: access_token=...;
  HttpOnly; Secure; SameSite=Lax` response header; change
  `get_current_user` to read the token from the cookie in addition to (or
  instead of) the `Authorization` header.
- Frontend: stop storing/reading the token in `localStorage`; the cookie is
  sent automatically by the browser. Remove the `auth.interceptor` token
  injection (cookie path obviates it).
- E2E tests: Playwright handles cookies automatically; no test changes needed
  if login response is parsed correctly.

**Done when:** logging out clears the cookie (server-side); a forged `<script>`
tag in user-controlled content cannot read the token; e2e suite still passes.

### 3. Refactor `backend/start.sh` inline DDL → Alembic migrations (~2–3 days)

**Why third:** the 22 inline `ALTER TABLE` + 2 `CREATE TABLE` blocks in
`backend/start.sh:99-786` run on every container boot with `# Don't exit` on
failure (lines 788–797). A corrupted migration silently passes `/health` and
serves traffic. This is the largest remaining operational footgun.

**Pre-existing artifact:** the full catalog of DDL statements is at
[`/tmp/eval_2026-05-18/3.3_deployment.md`](../../../tmp/eval_2026-05-18/3.3_deployment.md)
(may need re-running the audit if /tmp has been cleared). The estimate is 8–10
Alembic revisions.

**Scope per revision:**
1. Write `op.add_column(...)` / `op.create_table(...)` calls matching the
   inline SQL.
2. Test against a fresh dev DB: `alembic upgrade head` should leave the
   schema identical to what `start.sh` would produce.
3. For prod cutover: `alembic stamp <revision>` to mark prod as
   already-migrated (because the columns already exist via the inline DDL).
4. Once all revisions exist and prod is stamped, remove the inline blocks
   from `start.sh`. Replace `# Don't exit` with hard failure on migration
   error.

**Done when:** `start.sh` contains only `alembic upgrade head` (no inline
DDL), schema failures fail container startup loudly, and the prod DB is
stamped to the new head revision.

## Tier 2 — Meaningful improvements (do these after Tier 1)

### 4. Finish backend service coverage (#16 from May-18 audit) (~1 day)

Three services remain at <25% coverage:

- `sync_service.py` (155 LOC, 21% covered) — small, likely fast
- `report_service.py` (347 LOC, 19% covered) — medium
- `planning_center_sync_service.py` (1907 LOC, 22% covered) — large; needs
  HTTP mocking; the most valuable single bite

Pattern from the May-25 work on `enrollment_service`, `user_service`,
`progress_service` is well-established: read service → identify uncovered
methods → write tests covering happy + edge paths → run + commit. The first
two services in that batch surfaced real production bugs (silent soft-delete
failure on audit-log validation). Expect a similar yield here.

### 5. Karma specs for the 6 untested frontend component trees (~3–5 days)

`enrollments/`, `programs/`, `audit/`, `profile/`, `members/`, `activity-logs/`
have zero unit tests. The e2e suite is the only safety net for those surfaces.
One smoke test per component tree (render + happy path + error path) is the
floor; full behavioral coverage would be ~3 tests per component.

### 6. RDS `manage_master_user_password = true` (~2 hours)

Eliminates the manual three-step rotation ritual currently documented in
[`docs/RUNBOOKS/RDS_PASSWORD_ROTATION.md`](RUNBOOKS/RDS_PASSWORD_ROTATION.md).
AWS handles rotation; password lives only in an AWS-managed Secrets Manager
secret; no Terraform-state copy. Requires:

- Change `aws_db_instance.main` in `infrastructure/main.tf` to set
  `manage_master_user_password = true` (drop `password = random_password.db.result`)
- Remove `random_password.db` from `infrastructure/secrets.tf`
- The app's `DATABASE_URL` needs to read the password component from the
  AWS-managed secret at runtime (since it's now rotating). Either
  (a) refactor the app to assemble DATABASE_URL from components fetched at
  startup, or (b) add a Lambda that updates `app_secrets.DATABASE_URL` on
  RDS rotation event.

Option (a) is cleaner. Modest reward, modest blast radius once the runbook
exists as a fallback.

### 7. Redis-backed rate limiter (~1 day; needs new infra)

Today's rate limiter is `defaultdict(list)` in-memory (`main.py:191-251`).
Works because `desired_count = 1`. Breaks the moment ECS autoscaling adds a
second task — each task tracks its own limits, so the effective per-IP limit
doubles.

**Scope:**
- Provision ElastiCache Redis (`cache.t4g.micro`, ~$15/mo) in
  `infrastructure/`
- Switch backend to `slowapi` + `redis` or `fastapi-limiter` 
- Wire connection string into `app_secrets`

**Worth doing before** you have a reason to scale up — discovering this in
production under load is the worst-case path.

## Tier 3 — Hygiene + cleanup (do when you have spare cycles)

### 8. CSP tightening (~1 day)

Remove `'unsafe-inline' 'unsafe-eval'` from `script-src` in `main.py:118-129`.
Requires switching to nonce-based or hash-based script tags in the Angular
build. **Do this AFTER #2** — tightening CSP before moving the token out of
localStorage doesn't help. After #2, it's a meaningful defense-in-depth layer.

### 9. Split `planning_center_sync_service.py` (~3–5 days)

The single largest file in the codebase at 3,473 LOC. Cleanest split:

- `pc_http_client.py` — the HTTP/auth layer
- `pc_mappers.py` — translation between PC and internal schemas
- `pc_sync_jobs.py` — the long-running sync orchestration
- `pc_webhook.py` — webhook handling

Pure refactor — no behavior change. Worth doing for testability (smaller
modules = easier coverage) and for any future engineer who reads this code.
Likely also surfaces a few coverage gains as a side-effect.

### 10. Pre-deploy migration step (~1 day)

Today: `alembic upgrade head` runs on every container start. Works at current
scale; breaks the first time you have a migration that takes >30s (container
times out before it finishes). 

**Solution:** run migrations as a one-shot ECS task before the rolling update
of the main service. Two states:

1. Pre-deploy: `aws ecs run-task --task-definition migrations --launch-type FARGATE`
   then wait for `EXIT_CODE=0`
2. Then: `aws ecs update-service --force-new-deployment` (which proceeds
   without re-running migrations)

Worth designing now; implement when a migration with non-trivial runtime
makes it necessary.

### 11. Multi-stage `backend/Dockerfile.prod` (~2 hours)

Currently single-stage. Build deps (`gcc`, `g++`, `libpq-dev`) ship in the
runtime image. Multi-stage: stage 1 has build deps + runs `pip install
--prefix=/install`; stage 2 is `python:3.12-slim` with `apt-get install -y
libpq5 curl` and `COPY --from=builder /install /usr/local`. Shrinks image,
reduces attack surface, faster pulls.

### 12. Frontend quality sweep (parallel; varying effort)

Three related items, each independent:

- **`OnPush` change detection** on all components — easy 2x rendering perf win
  in components with lists or charts (dashboard, course content, etc.)
- **Subscription cleanup** — 62 `subscribe()` sites vs 7 `ngOnDestroy` /
  `destroy$` patterns. Memory-leak prevention. Most are fixable mechanically
  by switching template bindings to the `async` pipe.
- **E2E flake reduction** — 174 `waitForTimeout()` calls in the Playwright
  suite. Replace with `waitForSelector` / `waitForResponse` / `expect.poll`.
  Start with `course-content-advanced.spec.ts` (55 occurrences).

## Tier 4 — Architectural investment (months, not weeks)

### 13. Observability

App-level metrics dashboard: request latency by endpoint, DB query time,
login failures over time, Planning Center sync success rate. CloudWatch
Container Insights is the standard answer (intentionally disabled for cost
right now); alternative is OpenTelemetry to a self-hosted Grafana board.

### 14. Permissions matrix

Today's `admin/staff/instructor/viewer` boundaries are scattered across
endpoint files (and the May-25 work added another 9 modules' worth). A
single source of truth — either a decorator-driven system or a comprehensive
matrix doc — would make future endpoint additions mechanical. The work in
this session adding auth gates would have been faster with this in place.

### 15. SLO discipline

Not needed at current scale (single-church admin app at `desired_count = 1`).
But if usage grows, an SLO discipline (define "available," measure it, set
error budgets) is the difference between an app that ages well and one that
becomes a maintenance burden.

## What NOT to do

- **Don't start Tier 2 items before Tier 1 is done.** Test coverage is
  valuable but doesn't reduce active risk; the XSS CVEs do.
- **Don't bundle items across tiers** in a single PR. Keep each change
  focused so a failure in one doesn't force-rollback the others.
- **Don't pre-optimize for scale** you don't have. The Redis rate limiter is
  worth doing eventually, but only because it'll be too late if you wait for
  an actual scaling event.
- **Don't re-litigate already-closed items.** The May-9 evaluation flagged
  many items that the May-18 work closed; the May-18 evaluation flagged many
  items that this roadmap's prior session closed. Use those documents as
  historical context, not as a fresh to-do list.
